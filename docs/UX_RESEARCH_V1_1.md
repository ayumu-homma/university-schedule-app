# UX research and v1.1 proposal

Research date: 2026-10-12. Scope: official, public product documentation and accessible official help pages for seven schedule/planning products; product claims below describe what those sources document, not hands-on app testing. No third-party UI assets or screenshots are included. The editable synthetic before/after wireframe is [docs/ux/wireframes.svg](ux/wireframes.svg).

## Method and evidence labels

- **Documented**: stated in the linked official product source. When a product help page includes a screen image, this report uses its own textual labels and instructions; the asset is not copied.
- **Unverified**: the reviewed official public sources do not establish the item, or the referenced page was inaccessible / too sparse to inspect. This does not mean the product lacks the feature.
- **Inference**: design implications for UniSchedule derived from documented flows and the repository’s current implementation, not a claim about measured user outcomes.
- **Access actions** below count explicit taps or gestures after the app is open and the user is at the stated starting surface. They are documentation-derived path counts, not measured time, taps on device, or a universal count across app versions. Where documentation does not define a starting surface or a complete path, the count is marked n/a.

## What transfers to UniSchedule v1.1

The research points toward clear priorities rather than copying a competitor’s screen. Today should answer “what should I act on next?” before it shows the whole domain inventory. A timetable should preserve the student’s weekly class structure while providing enough detail for a selected course on phone layouts. Assignments and exams should feel like adjacent modes in one academic workload surface, and completion should explain what changed and provide a recoverable Undo action.

These recommendations are **design inference** from the documentation above and the current v1 source. The public sources do not establish that 3D helps students complete work or remember schedules. Three testable 3D hypotheses are listed below; each needs a 2D alternative and user testing. The v1.1 acceptance scope stays usable in 2D and does not depend on a 3D rendering or novel gesture.

## Wireframe and proposed design system

The editable synthetic SVG is organized into three Before → v1.1 pairs: Today, Timetable, and Assignments/Exams. “Before” is a schematic transcription of source-level structure, not an app capture. “After” depicts the proposal, not a released or tested screen. The art uses only generic shapes and synthetic Japanese example content.

Proposed components and token direction:

- Keep the existing 4/8 dp spacing rhythm, 48 dp touch minimum, semantic categories, light/dark colors and `ResponsiveContent` max width. Introduce screen composition helpers rather than a second token system: `TodayAtAGlanceCard`, `AcademicModeSwitch`, `SelectedCourseSheet`/details panel, compact section heading, and clear submission feedback.
- At 360–412 dp, prioritize title/time and actions. Do not shrink important Japanese text to fit a 5-column card; show a legible short course label in the grid, then full course/room/time in selected detail. Grid cells remain tappable/semantically labeled and all essential operations have visible controls.
- On tablet, center a bounded week grid and use the remaining width for selected-course details only when it improves scanability. At 840+ dp, keep text and navigation aligned to the content region rather than extending cards edge-to-edge.
- Use Material/system typography and scaling; avoid fixed heights around content. Category color always pairs with label/icon. Selection must use border/state/semantics as well as color.
- Motion is optional decoration. Use existing `AppMotion` values only for brief, interruptible transitions; honor reduced-motion signals and preserve an instantaneous state change path. No motion or 3D effect may be required for reading schedule state.
- Do not change auth, providers, repository, Drift schema, sync queue, RLS, privacy projection, offline behavior, or domain contracts in this UI pass.

## Acceptance map for the bounded slice

Run these after implementation, and retain evidence per layer. The current report is research and does not claim any item passed.

1. **Today summary and first use:** Widget tests with no data, normal data, overdue + today assignments, no classes, current/next class, and same-day event; verify summary is accurate to `TodayBriefing`, actions reach existing paths, empty-only categories do not dominate, all non-empty records remain reachable, loading/error surfaces reveal no exception details, and provider is still shared with Home.
2. **Timetable selection detail:** At 360 and 412 dp portrait, tap a long Japanese course and an empty slot; verify selected title/time/room are readable and non-destructive, detail opens from semantics keyboard action as well as touch, and existing add/detail/edit routes still work. At 840/1024 dp, verify a centered width and stable column scan. At phone landscape, ensure controls/grid/detail remain reachable without overflow or mandatory horizontal scroll.
3. **Assignment/exam mode and recovery:** Switch modes both directions and verify counts/date groups; create no test data in UI tests except synthetic fixtures. Complete a task with delayed success and failure, prevent duplicate submissions, show correct title/status, allow Undo to restore persisted status, then navigate away/back and confirm the expected state. Preserve assignment list’s today/week/open/done and course filters.
4. **Accessibility and device variants:** Exercise each touched screen at 360, 412, tablet and landscape sizes; light/dark; 200% text scaling; long Japanese titles, rooms and messages; `MediaQuery.disableAnimations=true`; minimum 48×48 dp bounds for every actionable control; meaningful semantics/order and label distinction for TalkBack; contrast for status/category colors. Assert no render exception, clipped mandatory content, offscreen-only actions, or horizontal overflow unless a labeled horizontal table interaction is explicitly retained.
5. **Privacy/offline/persistence guard:** Keep same authenticated schedule context and viewer projection. Test private and busy-only example records do not reveal titles/details in the proposed read-only timetable mode. Verify existing local data renders with network unavailable and that visual interactions do not enqueue a mutation until an existing explicit action is invoked.
6. **Implementation gates:** For the source change batch, run `flutter test` for affected widget tests and `flutter analyze`; run the repo’s prescribed full mobile checks at the acceptance boundary as appropriate. Check command, source hash, fixtures and environment in evidence. This research task ran no build or tests.

## 3D hypotheses (inference; not findings)

| Hypothesis | Possible value | Foreseeable harm | Minimum falsification test |
|---|---|---|---|
| 1. A shallow, rotatable campus-week “map” could help some students spatially remember where classes occur. | Could make time/day and building transitions salient for users who think spatially. | Rotating/scattered cards can obscure chronological order, demand motion, consume more pixels, worsen reduced-motion/accessibility and create the illusion of depth without new schedule information. | Compare 2D week grid to a static, non-rotating spatial metaphor with the same data; measure correct class/time/room lookup and completion of “what is next?” tasks, plus error and accessibility completion. Reject if it does not improve accuracy or time without loss. |
| 2. A 3D building/campus view could expose travel gaps between consecutive classes. | Could reveal adjacent building changes and tight transitions more intuitively than text alone. | The actual source model may have no campus coordinates, travel times or reliable room locations; guessed geography could mislead and expand sensitive location exposure. | Use synthetic campus coordinates clearly marked as mock; compare identifying an impossible transition against a labeled 2D route summary. Do not add real-location data until a trusted data source and privacy case exist. |
| 3. A depth effect on Today could make the nearest deadline feel urgent. | Might strengthen visual hierarchy for one urgent item. | Motion/scale may distract from due time, create false severity, reduce visible items and amplify anxiety; color/icon hierarchy is cheaper and accessible. | A/B test static hierarchy/card ordering first. Only compare a subtle optional effect if a non-motion equivalent exists; preserve equal color/labels and test reduced-motion. Default to 2D if evidence is mixed. |

No reviewed official source claims these 3D benefits. The v1.1 recommendation is to implement and validate the 2D acceptance scope first, then use opt-in, read-only, synthetic-data prototypes to decide whether any spatial metaphor merits further work. A successful 2D experience is the fallback and completion state.

## Limitations and open research questions

- This is independent official-document research. Dots research dispatch is unavailable in this task; no Dots findings or Dots consultation are claimed. Main is preparing any separately authorized private Dots packet/consult.
- No product app was installed, logged into, or interacted with. This is not a usability study and makes no claims about actual tap time, one-handed reach, error rate, display density, rendering performance, TalkBack traversal, or current release UI beyond published help content.
- TimeTree pages were updated in March 2026. Structured sources include September 2026 task/customization updates and a July 2025 accessibility overview. Todoist calendar docs were updated September 28, 2026 and recurring-completion docs October 7, 2026. Google Help pages were crawled on the research date, but the underlying product rollout may vary by account/locale. TickTick official page extraction was partial. Sugo Jika route yielded only an app-opening shell.
- Follow-up research after private Dots consultation should target actual student tasks and language; verify the value of a first-use Today summary, the course selection-detail pattern, and workload mode switching before adding deeper spatial metaphors.
